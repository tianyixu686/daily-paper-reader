## 摘要
基于图的检索增强生成（GraphRAG）在结构化语料库图上检索多跳问题的证据。现有的GraphRAG方法将证据发现与源溯源之间的联系隐式化。我们提出了LineageRAG，它为每个查询派生的证据需求构建一条证据谱系，并在所选证据支持该需求时，用逐字源片段完成该谱系。LineageRAG首先初始化证据需求。然后，通过需求条件化检索在语料库图上扩展每个谱系，同时保留与每个候选相关联的需求。谱系完成利用这一来源信息选择互补段落，并将受支持的需求扎根于逐字源文本中。在HotpotQA、2WikiMultiHopQA和MuSiQue上的实验表明，与领先的GraphRAG基线相比，LineageRAG在R@5、EM和F1上平均提高了3.51、5.96和5.22个百分点。

## Abstract
Graph-based Retrieval-Augmented Generation (GraphRAG) retrieves evidence for multi-hop questions over structured cor- pus graphs. Existing GraphRAG methods leave the connection between evidence discovery and source grounding implicit. We propose LineageRAG, which constructs one evidence lin- eage for each query-derived evidence demand and completes it with a verbatim source span when the selected evidence supports that demand. LineageRAG first initializes the evi- dence demands. It then expands each lineage through demand- conditioned retrieval over the corpus graph while retaining the demand associated with every candidate. Lineage completion uses this provenance to select complementary passages and grounds supported demands in verbatim source text. Experi- ments on HotpotQA, 2WikiMultiHopQA, and MuSiQue show that LineageRAG improves R@5, EM, and F1 by 3.51, 5.96, and 5.22 points on average over leading GraphRAG baselines.

### 1. 论文的核心问题与整体含义（研究动机和背景）

- **背景**：检索增强生成（RAG）为语言模型提供外部语料证据，但传统检索器独立打分难以应对多跳问题；GraphRAG 通过结构化图关系组织语料单元以支持多跳推理，代表方法包括 HippoRAG、PropRAG、HGRAG 等。
- **核心问题**：现有 GraphRAG 方法在证据发现与源文本验证（Source Grounding）之间存在断裂——图检索能找到相关候选，但最终证据集没有记录每一条证据服务于哪个具体证据需求。这会导致证据链不完整（论文图1展示了在 HotpotQA 上因漏检第二跳关键段落而回答错误的典型失败案例）。
- **整体含义**：论文提出 LineageRAG，仿照生物学和数据领域中的"谱系追踪"（Lineage Tracing）思想，为每个查询派生的**证据需求（Evidence Demand）**构建一条完整的证据谱系，从图检索逐步走向逐字源文本锚定，从而在多跳问答中同时提升检索覆盖率和答案质量。

### 2. 论文提出的方法论

LineageRAG 由三个阶段组成，核心思想是让每个证据需求的"身份标识"贯穿检索、选择、锚定全流程。

**阶段一：证据需求归纳（Evidence-Demand Induction）**
- 使用 LLM 将查询 q 映射为有序的证据需求序列 Rq = (r₁, ..., rₘ)，每个需求 rj = (idj, δj, Ij, Oj)：
  - δj：需求描述（该证据必须建立的事实）
  - Ij：该需求消费的符号变量（输入）
  - Oj：该需求应建立的符号变量（输出）
- 需求联合从原查询中归纳，不依赖已解析的中间值，标识符 idj 全程固定。

**阶段二：需求条件化谱系扩展（Demand-Conditioned Lineage Expansion）**
- 对每个需求独立调用图检索（使用 Personalized PageRank，基于查询 q 与需求描述 δj 作为种子）：Lj = RetrieveG(q, δj)。
- 各需求的检索结果按需求顺序深度优先合并形成候选池 Cq；每个候选段落保留其**溯源信息**：Aq(d) = {(idj, ℓ) | d = dj,ℓ}，记录该段落被哪个需求在什么排名位置检索到。
- 选择器表示 bq(d) 包含：溯源集合、曝光次数 nq(d)、最佳排名 ρq(d)、同标题冗余度 gq(d)。

**阶段三：带源溯源的谱系完成（Lineage Completion with Source Grounding）**
- **集合式选择（Set-wise Selection）**：LLM 依据候选的溯源信息，共同评估并选出 k 个能联合覆盖各证据需求的段落，鼓励互补、避免重复覆盖。
- **源锚定（Source Grounding）**：从选中段落中提取逐字（verbatim）源片段，建立标注 w = (iw, dw, sw, aw)，表示需求 iw 由段落 dw 中的片段 sw 所支撑；
- 有效性校验 Validq(w) 要求：片段确实在选中段落内（字符串包含校验）、类型标注符合 schema、且溯源连续性成立（即该段落确实为该需求被检索到过）。

该框架的核心创新在于：**需求—段落的关联从检索、选择一直到最终源锚定全程保留**，不像传统方法在某个环节丢失需求身份。

### 6. 论文的主要结论与发现

- **主结果**：LineageRAG 在三个数据集上的宏观平均 R@5 / EM / F1 达到 89.57 / 58.22 / 69.63，比最强 GraphRAG 基线（G-reasoner）平均提升 3.51 / 5.96 / 5.22 个点；在 GraphRAG 类方法的 9 个数据集—指标单元中 7 个排名第一。
- **消融**：除源锚定后检索 R@5 不变（76.53），但 EM 下降 6.20、F1 下降 5.65，说明其核心价值在**改善 reader 对证据的利用**而非单纯增加检索量；去需求归纳和去谱系扩展分别损失 0.92 和 2.15 个 R@5 点。
- **机制归因**：
  - 集合式选择本身贡献 1.30 个 R@5 点，证据谱系（需求—段落溯源）额外贡献 2.19 个点；
  - 溯源信息的**正确对应关系**至关重要：打乱溯源使 R@5 暴降 8.11 点（低于完全移除的 2.95 点损失）；
  - 与 QD+SETR 相比，LineageRAG 在同等池化 oracle 支持下选择损失更小（7.73 vs 8.79），即五段预算内的证据互补性更强；
  - 源锚定完成 1865/2182 个证据需求（85.5%），734/1000 个查询全部完成；500 条审计中 420 条完全支撑对应需求，10 条错误关联需求；
  - 锚定片段与需求之间的对应关系使 reader 输入从"整篇段落"变为"需求索引化的证据片段"，在检索完全不变的情况下显著提升 EM/F1。
- **成本结论**：相比 HippoRAG 2，仅以每查询 880 tokens 的额外开销换来 R@5 +3.53、EM +6.82、F1 +5.73 的增益，性价比合理。

### 7. 优点

1. **问题定位精准**：明确指出现有 GraphRAG 在"证据发现"与"源锚定"之间需求身份丢失的缺陷，并用直观失败案例佐证。
2. **概念新颖且类比自然**：借用谱系追踪（Lineage Tracing）概念，为 RAG 提出"证据谱系"这一清晰框架，需求 ID 全程跟踪的设计简洁而有效。
3. **机制分析深度突出**：表3–7 层层归因，从集合选择、需求分解、溯源信息三个维度逐步分离贡献，尤其是溯源"移除 vs 中性替换 vs 打乱"的对照设计非常严谨，有力证明了溯源信息确实是被"用对"而非单纯文本长度效应。
4. **源锚定设计可验证**：将最终证据限定为逐字（verbatim）源片段，并附加字符串包含校验、schema 校验和溯源连续性三重有效性检查，提升了推理结果的可审计性与可信度。
5. **公平对比意识强**：与 HippoRAG 2 共享图索引和检索设置，同 reader、同查询划分，使主要增益可归因于框架本身而非实现差异。
6. **成本透明**：提供完整 token 消耗明细，便于后续研究评估性价比。

### 8. 不足与局限

1. **计算资源信息缺失**：未报告 GPU 型号、数量、训练/推理耗时等硬件细节，影响可复现性和资源评估。
2. **评测规模有限**：每数据集仅 1000 条查询，未覆盖全部测试集；未验证在单跳问答、开放域问答、跨语言或多模态场景中的表现。
3. **基线可比性不完全一致**：ETS-7B、Relink 为原生 reader 的发表结果，与统一协议下重测的方法比较时存在不公平因素。
4. **依赖 LLM 组件的级联误差**：需求归纳、集合选择、源锚定三次生成调用均依赖 LLM，任一环节出错都会向下传播（如 500 条审计中仍有 20 条锚定片段未建立完整事实、10 条关联错误需求）。

6. **查询时延迟增加**：查询时 token 消耗是 HippoRAG 2 的 2.4 倍，且是多阶段串行 LLM 调用，实际延迟和工程部署成本可能高于 token 数字所示。
7. **适用范围局限**：依赖图索引的质量（OpenIE 抽取），对关系抽取误差敏感；源锚定仅支持逐字片段，面对多文档综合、隐含推理等需求时能力边界未讨论。
