## 摘要
在企业环境中部署的智能体必须在结构化API和文档集合之间进行推理，然而现有基准测试将这些能力孤立地评估。我们引入VAKRA（评估API和知识检索智能体），一个涵盖62个领域、超过8000个可执行API的基准，任务跨越三个难度递增的设置：多样化的API交互风格、结构化API上的多跳推理，以及带有自然语言工具使用策略约束的多源推理。正确性通过针对实时API重新执行预测的工具调用来验证，并容纳多种有效路径。使用固定的ReAct框架将模型能力与智能体架构隔离，我们评估了前沿和开放权重模型，发现即使是最好的模型在单跳端点式任务上也仅达到70.4%，在组合API上降至50-51%；随着推理深度增加，性能下降超过50%，而策略约束问题暴露出严重失败（在无法回答的查询上低至2.4%）。痕迹分析显示，失败集中在语言中介的推理——实体消歧、跨源基础定位，而非工具调用机制。代码可在 https://github.com/IBM/VAKRA 获取。数据集可在 https://huggingface.co/datasets/ibm-research/VAKRA 获取。

## Abstract
Agents deployed in enterprise settings must reason across structured APIs and document collections, yet existing benchmarks evaluate these capabilities in isolation. We introduce VAKRA (e\textbf{V}aluating \textbf{A}PI and \textbf{K}nowledge \textbf{R}etrieval \textbf{A}gents), a benchmark of over $8{,}000$ executable APIs across $62$ domains with tasks spanning three settings of increasing difficulty: diverse API interaction styles, multi-hop reasoning over structured APIs, and multi-source reasoning with natural-language tool-use policy constraints. Correctness is verified by re-executing predicted tool calls against live APIs, accommodating multiple valid paths. Using a fixed ReAct harness to isolate model capabilities from agent architecture, we evaluate frontier and open-weight models and find that even the best model achieves only 70.4\% on single-hop endpoint-style tasks and drops to 50--51\% on compositional APIs; performance degrades by over 50\% as reasoning depth increases, and policy-constrained questions expose severe failures (as low as 2.4\% on unanswerable queries). Trace analysis shows failures concentrate at language-mediated reasoning - entity disambiguation, cross-source grounding, rather than tool invocation mechanics. Code is available https://github.com/IBM/VAKRA. Dataset is available https://huggingface.co/datasets/ibm-research/VAKRA

## 1. 核心问题与研究动机

- **背景**：企业级 AI 智能体（agent）在实际部署中必须同时处理结构化 API 调用与文档集合检索，例如客户投诉处理、商业智能分析、财务运营等。这些任务往往需要多步推理、跨源信息整合以及遵守自然语言描述的工具使用策略。
- **问题**：现有基准测试将工具调用、多跳文档检索、网页导航、策略遵守等能力**割裂评估**，缺乏一个能够在同一推理链中综合检验这些能力的可执行基准。这导致实际部署中约 75% 的团队在没有正式基准的情况下评估智能体。
- **目标**：作者提出 **VAKRA**（e**V**aluating **A**PI and **K**nowledge **R**etrieval **A**gents）基准，用于在一个统一的、真实可执行的环境中评估智能体在“跨 API 与文档检索的多跳推理 + 工具使用策略约束”下的表现，并定位失败发生的具体环节。

## 2. 方法论

- **核心思想**：构建一个本地自托管、基于真实数据库的可执行工具环境，并生成需要多步推理、跨 API/检索源组合的任务链，通过**重新执行预测的工具调用**来验证轨迹正确性，而非仅比对最终答案。
- **基准构成**：
  - 基于 BIRD-SQL 真实数据库，将结构化查询转换为 **8,000+ 个可执行 Python API**，覆盖 **62 个领域**。
  - 利用 ClapNQ 与 Wikidata5M 构建领域对齐的检索文档集合，通过 ChromaDB 提供语义检索工具。
  - 所有工具通过 Docker 容器本地部署，使用 MCP（Model Context Protocol）通信，数据库与索引不直接暴露给智能体，保证可复现和确定性。
- **任务设置（三档难度递增）**：
  1. **API 交互风格**：包含三类接口——
     - **SLOT**：9 个通用操作（过滤、聚合等），需组合成多步链；参数多，需规划。
     - **SEL**：26 个展开的具体工具，单次调用简单但选择空间大。
     - **Dashboard（端点式）**：每个样本平均 116 个高度定制化端点，挑战在于查询解析和端点选择。
  2. **多跳推理**：构造 2–5 跳的 API 调用链，上一跳输出参数化下一跳输入，涉及实体消歧、中间结果抽取、跨端点 schema 对齐。
  3. **多源推理（含策略）**：要求在同一轨迹中交替使用结构化 API 与文档检索，并可能附带自然语言**工具使用策略**（例如“禁止使用文档回答电影相关问题”），策略可能使问题不可回答或改变答案来源。
- **数据生成流水线**：
  1. 从 BIRD-SQL 查询中抽取命名实体，映射到 Wikidata5M 标识，构建领域知识图谱。
  2. 通过查询连通图做深度优先遍历，采样 1–3 跳（权重 0.10/0.60/0.30），用 LLM 生成合并后的自然语言查询。
  3. 引入检索增强边，生成 API+RAG 联合推理问题。
  4. 生成纯检索多轮对话，并做交叉源可回答性过滤，保证 API/RAG 问题不能互相回答。
  - 生成过程中使用 LLM 过滤文档，避免检索源能直接回答 API 问题，降低捷径污染。
- **评估框架**：采用瀑布式三级判定——
  1. **工具序列验证**：重新执行预测的工具调用，先程序化 containment 检查，不明确时用 LLM judge（基于 CRAG 框架）判断是否获取所有必要信息。
  2. **最终响应评估**：检查最终答案是否 grounding 于工具输出，以及事实一致性（基于 RAGAS answer correctness）。
  3. **策略遵守**：确定性检查是否访问了不允许的源，与答案正确性无关。
  - 使用固定 **ReAct** harness 封装所有模型，隔离模型能力与架构差异，保证公平性。
- **模型不可知设计**：提供统一 `AgentInterface`，支持 Anthropic、OpenAI、Ollama、LiteLLM、watsonx 等来源，MCP 工具自动转换为带完整参数签名的 LangChain StructuredTool。

## 6. 主要结论与发现

- **总体表现不佳**：最强模型 GPT-5.5 在单跳端点式 Dashboard 任务上仅 70.4%，在组合式 BI API（SEL/SLOT）上降至 50–51%，多源多跳仅 26.0%。
- **推理深度导致显著衰减**：除 GPT-5.5 外，几乎所有模型在跳数增加时损失超过 50% 准确率；2 跳 API 问题相比 1 跳明显下降。
- **API 交互范式影响模型排名**：模型在 Dashboard 与 BI API 上的表现排名差异很大，例如 Granite-4h-small 在 Dashboard 上优于 Qwen-3.5-397B，但在 BI API 上垫底，说明不存在统一的“工具使用能力”。
- **失败集中在语言中介推理**：工具识别和参数填充的误差相对较小，主要瓶颈在于实体消歧、跨源 grounding、schema 对齐；在多源任务中，当 RAG 后接 API 时，约 70–75% 的错误来自答案抽取/grounding。
- **工具使用策略遵守是严重短板**：当策略使问题不可回答时，Claude-Opus-4.7 仅 2.4% 准确率，GPT-5.5 也仅 3.7%，模型往往强行给出答案而忽略“不可回答”约束。
- **幻觉是主要错误来源**：在 BI 与 Dashboard API 的 grounded 错误中，幻觉占比显著高于抽取错误；Dashboard API 还出现较多长响应截断导致的抽取失败。
- **检索相关任务表现不稳定**：部分模型（如 Gemini-3-Flash-Preview）在 2-hop RAG-API 上出现尖峰，可能与单跳 API 能力较强有关；LLaMA-3.3-70B-Instruct 和 Qwen-3.5-397B 在纯 RAG 跳上表现较好，但整体仍较弱。

## 7. 优点

- **真实可执行环境**：所有 API 基于真实数据库本地部署，结果可重新执行、可验证、无外部依赖，规避了模拟反馈或 API 漂移问题。
- **组合性挑战全面**：首次将嵌套 API 序列、多跳推理、跨源检索、自然语言策略遵守统一到一个基准中，更加贴近企业级实际场景。
- **轨迹级验证**：不仅检查最终答案，还验证工具调用序列是否正确，且允许多条有效路径，评判更具包容性。
- **错误归因清晰**：通过瀑布式分级和错误类型分析，能定位失败发生在工具选择、参数值、答案抽取还是策略遵守，有助于后续针对性改进。
- **模型隔离**：固定 ReAct harness，并将工具定义为完整参数签名的结构化工具，公平比较不同来源、不同规模的模型。
- **数据质量控制**：含人工评估和交叉源可回答性过滤，降低合成数据泄漏与捷径风险，这一点优于多数自动生成基准。

## 8. 不足与局限

- **数据构建的合成性**：查询由 LLM 生成、合并，虽经人工抽样验证，但仍有潜在幻觉、逻辑不一致或数据泄漏风险，且人工审查规模有限（每设置 60 题）。
- **单一 agent 框架**：仅使用 ReAct，未探索其他规划/反思架构；结论可能不完全适用于所有 agent 设计范式。
- **LLM-as-judge 偏差**：阶段 1/2 使用 GPT-OSS-120B 作为 judge，存在 judge 对特定模型输出风格偏差的可能性；未报告 judge 与人类评估的一致性验证。
- **模型覆盖不全**：Claude-Opus-4.7 仅在子集上评估；部分模型（如 GPT-5.5）的分数差距可能受 API 版本、温度、部署环境差异影响，论文未详细说明。
- **领域覆盖受限**：API 来自 BIRD-SQL 数据库，文档来自 ClapNQ/Wikidata5M，虽覆盖 62 个领域，但仍以公开知识库为主，缺少真实企业私有数据、权限系统、动态业务逻辑的复杂度。
- **策略设计较简单**：工具使用策略主要体现为“允许/禁止哪些源”，未覆盖更复杂的预算、优先级、并发或安全约束；策略推理的测试深度有限。
- **计算资源公开不足**：未披露推理成本、GPU 配置等，复现成本难以预估；数据生成与评测的 token 消耗也未报告。
